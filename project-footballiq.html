FootballIQ

An AI-powered football analytics platform combining a medallion data warehouse, XGBoost valuation models, and a RAG-powered analyst grounded in SQL.

Overview

FootballIQ is a full-stack football analytics platform built to turn raw match and player data into decision-ready insight. It is structured as an 11-module system on Clean/Hexagonal Architecture, so the domain logic — player valuation, squad analysis, natural-language querying — stays independent of any particular database, API framework, or frontend.

Problem

Football analytics tools tend to either expose raw stats with no interpretation, or lock insight behind opaque black-box models. Analysts and fans alike lack a single place to get an explainable player valuation and ask follow-up questions in plain language, backed by the actual underlying data rather than a hallucinated summary.

Approach

Data flows through a medallion warehouse (bronze/silver/gold layers) built with dbt on PostgreSQL, ingesting FIFA 2026 data covering 48 teams and 1,248 players. An XGBoost model produces player valuations, with SHAP used to explain each prediction feature-by-feature rather than as an opaque number. A retrieval-augmented generation layer sits on top of pgvector, grounding the conversational analyst's answers in real SQL query results instead of free-form generation. The Next.js frontend consumes all of this through a clean API layer, and GitHub Actions runs the CI pipeline before every deploy to Neon (database), Render (API), and Vercel (frontend).

Results

The system ships with 154 automated tests at 92% coverage across its 11 modules, and is deployed and publicly reachable, serving live player valuations and natural-language queries grounded in the underlying warehouse data.

Challenges

The hardest part was keeping the RAG analyst honest: instead of letting the language model free-associate about football, the pipeline forces a strict retrieval-then-generate flow where the model only summarizes SQL results it was actually given. Maintaining 92% test coverage across 11 independently deployable modules also required disciplined contract testing at every module boundary, so a change in one layer couldn't silently break another.
